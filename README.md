# CLI Weather Digest

Консольная утилита на Node.js для получения прогноза погоды по одному или нескольким городам через открытый REST API [Open-Meteo](https://open-meteo.com/). Утилита получает координаты города (geocoding), затем прогноз погоды по координатам, выводит результат в читаемом виде в терминал и сохраняет отчёт в файл.

## Требования к окружению

- Node.js версии 20 и выше (используется встроенный `fetch`, сторонние HTTP-клиенты не используются)
- npm

## Установка

```bash
npm install
cp .env.example .env
```

Значения в `.env` по умолчанию уже указывают на реальные публичные эндпоинты Open-Meteo и рабочий таймаут, поэтому менять их не обязательно для локального запуска.

## Тесты

```bash
npm test
```

Покрыты валидация CLI-аргументов (`parseDays`/`parseCity`), разбор ответа API и обработка HTTP-ошибок (`fetchWrapper`), а также обработка сценария "город не найден" и независимость обработки нескольких городов (`services`). Тесты также запускаются автоматически в pre-commit hook.

## Переменные окружения

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `BASE_GEOCODING_URL` | Базовый URL geocoding-API (получение координат по названию города) | `https://geocoding-api.open-meteo.com/v1/` |
| `BASE_FORECAST_URL` | Базовый URL forecast-API (получение прогноза по координатам) | `https://api.open-meteo.com/v1/` |
| `TIMEOUT` | Таймаут запроса в миллисекундах | `5000` |
| `REPORTS_DIR` | Каталог, куда сохраняются отчёты/кэш | `reports` |

## Команды запуска

```bash
npm start -- --city "Moscow" --days 3
```

Параметры:
- `--city <города>` — **обязательный**. Одно название или несколько через запятую: `--city "Moscow,Paris"`
- `--days <число>` — необязательный, по умолчанию `3`, допустимый диапазон `1-7`
- `--no-cache` — необязательный, принудительно выполняет сетевой запрос, игнорируя сохранённый кэш за сегодня

Примеры:
```bash
npm start -- --city "Moscow" --days 5
npm start -- --city "Moscow,Paris,asdkjaskjd"
npm start -- --city "Moscow" --no-cache
```

## Запуск через Docker

```bash
docker compose run --rm weather --city "Moscow" --days 3
```

Именно `run`, а не `up` — `up` не принимает аргументы командной строки. `--rm` удаляет контейнер после завершения. Каталог `reports/` смонтирован как volume, кэш и отчёты сохраняются между запусками.

├─────────┼──────────────┼──────────────────────────┼─────────────────────────┼───────────────┤

## Обработка ошибок

Обрабатываются следующие сценарии, каждый с понятным сообщением на русском, без стек-трейса:

| Сценарий | Пример |
|---|---|
| Отсутствующий/некорректный аргумент | нет `--city`; `--days` не число или вне диапазона 1-7 |
| Город не найден | пустой результат geocoding-запроса |
| Ответ со статусом 4xx | некорректные параметры запроса |
| Ответ со статусом 5xx | ошибка на стороне сервера |
| Отсутствие сети | недоступен хост / DNS не резолвится |
| Превышение таймаута | сервер не ответил за отведённое время (`TIMEOUT`) |
| Некорректный JSON в ответе | тело ответа нельзя распарсить |

Сообщения об ошибках для конкретного города включают название города (`[Moscow] Город не найден`) — это важно при параллельной обработке нескольких городов, чтобы понимать, к какому из них относится ошибка.

**Код завершения:** `0` — успех, `1` — если хотя бы один запрошенный город завершился ошибкой.

## Структура проекта

```
src/
├── index.ts        # точка входа: разбор и валидация CLI-флагов, запуск
├── error.ts         # кастомные классы ошибок (TimeoutError, NetworkError, HttpError, JSONError, MissingCityError)
├── types.ts          # общие типы ответов API
├── api/               # клиент внешнего API (geocoding, forecast, общая обёртка с таймаутом и переводом ошибок)
├── services/          # бизнес-логика: оркестрация запросов по городу, кэш, Promise.allSettled
├── storage/            # чтение/запись кэша и отчётов в файловую систему
└── format/              # форматирование читаемого вывода в консоль
```

## Архитектурные решения и известные ограничения

- **TypeScript** выбран вместо обычного JS ради типобезопасности при работе с ответами внешнего API: на практике это не раз помогало ловить реальные ошибки (несоответствие типов, забытые поля) ещё на этапе разработки, а не в рантайме.
- **`commander`** выбран для парсинга CLI-флагов вместо ручного разбора `process.argv`. Это популярное, проверенное решение, которое берёт на себя часть валидации "из коробки" (например, отсутствие обязательного `--city`), оставляя более тонкую логическую валидацию (диапазон `--days`, непустой список городов) на собственные парсеры.
- **Модули разложены по слоям с однонаправленной зависимостью:** `index.ts` (CLI) → `services/` (бизнес-логика) → `api/`/`storage/` (данные), а `format/` только форматирует уже готовый результат. Нижние слои не знают о том, кто их вызывает. Например, `services/` не печатает ничего в консоль, это исключительно задача `format/`.
- **Ошибки оформлены через собственные классы** (`TimeoutError`, `NetworkError`, `HttpError`, `JSONError`, `MissingCityError`), а не через голый `Error`. Это позволяет различать сценарии через `instanceof`, вместо разбора текста сообщения или множества разрозненных проверок.
- **Единая точка перехвата ошибок** — это отдельное от классов решение: перевод сырых ошибок в свои классы происходит близко к источнику (`fetchWrapper`), а вот решение, что показать пользователю и с каким `exit code` завершиться, принимается один раз, наверху (`index.ts`), а не размазано по всей цепочке вызовов.
- **Таймаут явно отличим от сетевой ошибки** — это два разных класса с разными сообщениями пользователю ("Превышено время ожидания" vs "Проблема с сетью"), а не один общий текст на любой сетевой сбой.
- **`docker compose run`, а не `up`** — `up` предназначен для долгоживущих сервисов с фиксированной конфигурацией и не принимает аргументы при запуске. `run` рассчитан на одноразовое выполнение команды с конкретными параметрами, что соответствует функционалу этой утилиты. Она выполняется и завершается, а не работает постоянно как сервис.
- **Общая обёртка `fetchWrapper<T>`** инкапсулирует таймаут, проверку статуса и перевод сырых ошибок в одном месте, вместо дублирования этой логики в `geocoding.ts` и `forecast.ts` по отдельности.
- **`dns.setDefaultResultOrder('ipv4first')` вызывается при старте** — на некоторых машинах со сломанной/нестабильной поддержкой IPv6 сетевые запросы Node.js могут зависать до срабатывания таймаута, хотя тот же адрес доступен через `curl`/браузер. Это решено программно один раз при запуске, а не переложено на пользователя через переменные окружения.
- **Обязательные переменные окружения проверяются при старте**, до любой сетевой активности — если `BASE_GEOCODING_URL`/`BASE_FORECAST_URL` не заданы, утилита сразу завершается с понятным сообщением, вместо непонятной ошибки где-то в середине выполнения. `TIMEOUT` не входит в обязательные — при его отсутствии используется фолбэк по умолчанию (`5000`).
- **Biome** используется вместо ESLint+Prettier — решает и линтинг, и форматирование одним быстрым инструментом вместо двух отдельных пакетов с раздельной конфигурацией.
- Использован **npm**. Рассматривался переход на pnpm, но для проекта такого масштаба (одна утилита, немного зависимостей) выигрыш не оправдывает дополнительный инструмент, поэтому остались на дефолтном менеджере.
- **Кэш инвалидируется по дате в имени файла** (`{город}-{ГГГГ-ММ-ДД}.json`), а не по TTL — дата "протухает" сама по себе: если файла с сегодняшней датой нет, это естественно трактуется как отсутствие кэша.
- Если в кэше сохранено **меньше** дней, чем запрошено, то данные докачиваются из сети и кэш обновляется; если **больше** — лишние дни обрезаются без похода в сеть.
- Битый или отсутствующий файл кэша не приводит к падению программы, в обоих случаях это тихо трактуется как "кэша нет", и выполняется обычный сетевой запрос.
- Названия городов приводятся к нижнему регистру перед сохранением в кэш, что устраняет дублирование кэша из-за разного регистра ввода (`Moscow`/`moscow`), но **не решает** случай разных названий одного города на разных языках (`Moscow`/`Москва`). Это осознанное ограничение, а не недосмотр: для устранения потребовался бы дополнительный сетевой запрос, что противоречит самой идее кэширования.
- Настроен pre-commit hook (Husky + lint-staged) — прогоняет линтер и проверку типов перед каждым коммитом; это не требуется явно заданием, но снижает риск закоммитить код с ошибками.
